Eventos discretos en juegos

Un juego tiene un game loop a 60 cuadros por segundo, así que no parece un simulador de eventos discretos. Pero adentro hay muchas cosas que no necesitan revisarse cada cuadro: un edificio que termina en 4 horas, el turno del próximo personaje, un buff que vence en 10 segundos, el próximo choque entre dos bolas. Todas son eventos con un tiempo, y todas se resuelven con lo que vimos: una cola de prioridad y un reloj que salta.

Progreso offline: lo que pasó mientras no jugabas

En los idle games y en los juegos de construcción para celular, cerrás la app y al volver la granja produjo, la mina extrajo y el edificio se terminó. El juego no estuvo corriendo: al abrirse, simula de golpe todo lo que pasó. Con un loop de paso fijo serían millones de cuadros. Con eventos, solo los momentos en que algo cambió.

Acá: cada granja da 1 de comida cada 5 s; la mina consume 1 de comida y da 2 de oro cada 9 s (si no hay comida, espera); con 20 de oro se construye una granja nueva, que tarda 2 minutos. Los eventos se encadenan: más granjas, más comida, más oro, más granjas.

function ponerseAlDia(estado, segundosAfuera) {
  const fin = estado.reloj + segundosAfuera;
  while (estado.agenda.size && estado.agenda.peek().t <= fin) {
    const ev = estado.agenda.pop();
    estado.reloj = ev.t;

  }

}
Muchos juegos lo resuelven con una cuenta ("producción por segundo × segundos afuera"), que es instantánea pero solo funciona si nada depende de nada. En cuanto la mina necesita comida y la comida depende de cuántas granjas hay, la cuenta se equivoca. La simulación por eventos da exactamente lo mismo que si el jugador hubiera tenido el juego abierto.

Turnos por velocidad

En Final Fantasy X o en Honkai: Star Rail, los personajes rápidos actúan más seguido. La barra de "próximos turnos" que muestra la interfaz es literalmente una cola de prioridad: cada personaje tiene agendado su próximo turno en t + 100 / velocidad. Cuando actúa, se vuelve a agendar. Un hechizo de prisa o de lentitud cambia la velocidad y reprograma su turno.

Timers y cooldowns sin revisar todo cada cuadro

Lo más común en un juego en tiempo real es un híbrido: el game loop sigue a paso fijo, pero todo lo que "pasa dentro de X segundos" va a una agenda. Cada cuadro se sacan los eventos vencidos y nada más. Con 10.000 enemigos con buffs, el costo depende de cuántos buffs vencen en ese cuadro, no de cuántos hay.

const agenda = new MinHeap((a, b) => a.t - b.t || a.seq - b.seq);
let ahora = 0, seq = 0;
const despues = (seg, fn) => agenda.push({ t: ahora + seg, fn, seq: seq++ });

function update(dt) {
  ahora += dt * escalaDeTiempo;                      // pausa y cámara lenta gratis
  while (agenda.size && agenda.peek().t <= ahora) agenda.pop().fn();
  // ... física, input, render a paso fijo
}

despues(10, () => jugador.escudo = false);          // el escudo dura 10 s
despues(0.8, () => torreta.puedeDisparar = true);   // cooldown

setTimeout es exactamente esto, pero usa el reloj de la computadora. Con una agenda propia, el tiempo es el del juego: se pausa con el juego, se acelera con él y se puede guardar en una partida o reproducir en un replay.

Colisiones por eventos: billar sin tunneling

Con paso fijo, la física pregunta en cada cuadro "¿se están tocando?". Si una bola va rápido y la pared es fina, en un cuadro está de un lado y en el siguiente del otro, y nunca se tocaron: es el tunneling. La alternativa por eventos calcula cuándo va a ser el próximo choque (de bola con bola y de bola con pared, resolviendo una cuadrática), lo agenda y salta hasta ahí. No se le escapa ningún choque, a cualquier velocidad.

Un detalle: cuando dos bolas chocan, cambian de dirección, y los choques que tenían agendados ya no valen. En vez de buscarlos en el heap y borrarlos, cada bola lleva un contador de choques. Si al sacar un evento los contadores no coinciden con los de cuando se agendó, se descarta (invalidación perezosa).

// ¿en cuánto tiempo chocan las bolas a y b? (null si nunca)
function tiempoHastaChoque(a, b) {
  const dx = b.x - a.x, dy = b.y - a.y, dvx = b.vx - a.vx, dvy = b.vy - a.vy;
  const dvdr = dx * dvx + dy * dvy;
  if (dvdr >= 0) return null;                          // se están alejando
  const dvdv = dvx * dvx + dvy * dvy, drdr = dx * dx + dy * dy, s = a.r + b.r;
  const d = dvdr * dvdr - dvdv * (drdr - s * s);
  if (d < 0) return null;                              // se cruzan sin tocarse
  return -(dvdr + Math.sqrt(d)) / dvdv;
}
// evento válido solo si nadie chocó desde que se agendó

Historias que se escriben solas

Los simuladores de colonia y de mundos usan eventos para generar historia. En RimWorld, los incidentes (incursiones, enfermedades, visitas) se definen con un tiempo medio entre eventos, es decir, esperas exponenciales como las del capítulo 1, y el "narrador" ajusta ese ritmo según cómo le va a la colonia. Dwarf Fortress genera siglos de historia del mundo antes de que empiece la partida, saltando de evento en evento.

El Simulador de Comunidad 3000 AC, que está en la carpeta de la unidad (Discrete_event_sim/simulador de historia de pueblo), hace eso con una aldea prehistórica: las personas tienen necesidades (hambre, sed, frío, soledad), eligen acciones que duran un tiempo, y cada acción es una cadena de eventos: DecideActionEvent agenda un ActionCompleteEvent para cuando termine, y ese agenda la próxima decisión. Cada 12 horas un SocialCheckEvent revisa los vínculos. Aparte, un evento aleatorio cada 50 horas en promedio (exponencial) trae descubrimientos o noches frías. Afinidades, parejas, nacimientos y muertes salen de ahí sin que nadie los programe uno por uno. Todo pasa por un MinHeap con desempate por seq.
