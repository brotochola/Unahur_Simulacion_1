Layout benchmark

8× typed array (SoA) vs 1× typed array (bitmask)

Same job — store 8 boolean properties per entity, then write and read all 8 of them for every entity, in order. One approach uses eight separate typed arrays, one per flag. The other two pack all eight flags into a single element per entity: one builds the value in a local variable before a single store (bulk set), the other reads, modifies, and stores the value back for each individual flag (read-modify-write). Pick the element type below — Uint8/Int8/Uint16/Int16/Uint32/Int32/Float32/Float64 are all supported. Timed in your browser, on your hardware.

En español: el mismo trabajo — guardar 8 propiedades booleanas por entidad, y luego escribir y leer las 8 para cada entidad, en orden. Un enfoque usa ocho arreglos tipados separados, uno por bandera (SoA). Los otros dos empaquetan las ocho banderas en un solo elemento por entidad: uno arma el valor entero en una variable local antes de guardarlo de una vez ("bulk set"), y el otro lee, modifica y vuelve a guardar el valor por cada bandera individual ("read-modify-write" o RMW), que es el patrón más realista si cada propiedad se cambia por separado en distintos momentos. Elegí el tipo de elemento más abajo — soporta Uint8/Int8/Uint16/Int16/Uint32/Int32/ Float32/Float64. Todo se mide en tu propio navegador, con tu propio hardware.

SoA — 8× typed array
Bitmask (bulk set) — 1× typed array
Bitmask (RMW) — 1× typed array

Each "op" below = one flag read or write for one entity, so N = 1,000,000 means 8,000,000 ops per write pass and 8,000,000 ops per read pass. Every combination is warmed up once (untimed) before timed trials to reduce JIT-compilation noise; the reported time is the median of the trials. Read passes accumulate a checksum so the engine can't optimize the loop away. Memory shown is raw bytes allocated for the flag storage only (SoA needs elementSize bytes per flag per entity; bitmask needs elementSize bytes per entity total, for up to 8 flags). Bitmask (RMW) uses the same single array as Bitmask (bulk set) — same memory — it only differs in how the write loop touches it.

Data type picks the element type used to allocate every array in the run — for SoA it's the type of each of the 8 flag arrays; for both bitmask variants it's the "word" each entity's packed byte lives inside (still only 8 bits are ever used, so Uint16/Uint32 words waste the extra bits — included so you can see that cost directly in the memory readout and, usually, in write/read time too). Signed vs unsigned integer types (Int8 vs Uint8, etc.) behave identically for the bit operations here, since JS bitwise operators always work on the raw 32-bit two's-complement bits regardless of the typed array's signedness. Float32/Float64 are only run for SoA — bitmask needs integer bit operations, and JS's bitwise operators coerce every operand to a 32-bit integer first, so packing into a float array wouldn't measure what it claims to; the bitmask bars are hidden for those two types.

En español: cada "op" (operación) es una lectura o escritura de una bandera para una entidad, entonces N = 1.000.000 significa 8.000.000 de operaciones en el paso de escritura y 8.000.000 en el de lectura. Cada combinación se "calienta" una vez sin medir antes de las pruebas cronometradas, para reducir el ruido de la compilación JIT; el tiempo mostrado es la mediana de las pruebas. Los pasos de lectura acumulan un checksum para que el motor no pueda optimizar y eliminar el bucle. La memoria mostrada son los bytes crudos asignados solo para las banderas (SoA necesita elementSize bytes por bandera por entidad; el bitmask necesita elementSize bytes por entidad en total, para hasta 8 banderas). Bitmask (RMW) usa el mismo arreglo único que Bitmask (bulk set) — misma memoria — solo cambia cómo el bucle de escritura lo toca.

Tipo de dato elige el tipo de elemento usado para reservar cada arreglo de la corrida — para SoA es el tipo de cada uno de los 8 arreglos de banderas; para las dos variantes de bitmask es la "palabra" donde vive el byte empaquetado de cada entidad (siempre se usan solo 8 bits, así que palabras Uint16/Uint32 desperdician los bits extra — se incluyen justamente para que veas ese costo reflejado en la memoria y, normalmente, también en el tiempo). Los tipos con o sin signo (Int8 vs Uint8, etc.) se comportan igual en estas operaciones de bits, porque los operadores bitwise de JS siempre trabajan sobre los 32 bits en complemento a dos, sin importar el signo del arreglo tipado. Float32/Float64 solo corren para SoA — el bitmask necesita operaciones de bits sobre enteros, y los operadores bitwise de JS convierten cada operando a un entero de 32 bits primero, así que empaquetar en un arreglo de floats no mediría lo que dice medir; las barras de bitmask se ocultan para esos dos tipos.
